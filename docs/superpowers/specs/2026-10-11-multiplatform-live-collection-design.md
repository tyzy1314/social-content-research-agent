# 多平台实时采集设计

## 目标

提供一个多平台统一的实时采集入口。用户可以选择单个平台，也可以选择全部平台；一次运行按平台分别报告成功、需登录/授权、受限或暂不支持的原因。适配器入口不等于平台都能实时采集，不能把未取得的数据伪装成成功。

## 当前代码与问题

- `main.py` 的 `crawl` 主要连接旧采集流程；新 `platform_service.collect_platform_comments()` 已能把内容和评论写入统一库，但没有面向普通 CLI 的统一入口。
- 小红书适配器已有可见浏览器采集代码，不过能力接口目前只返回访问状态，没有把登录态搜索、详情和评论作为统一 `AccessResult` 数据提供给 `platform_service`。
- B 站有公开 API 适配；访问被 HTTP 412、403 或 429 拒绝时必须停止，不做重试或绕过。
- 其他平台保留现有接入状态。缺少合法、已实现的实时路径时，本轮只报告原因，不新造采集接口。

## 方案

新增一个 `main.py collect-live` 命令，复用现有 `ADAPTERS`、`PLATFORM_ORDER`、`platform_service` 和 `unified_store`，不再建第二套平台注册或数据层。小红书继续走现有 `CrawlerEngine` 浏览器流式采集；采集后调用已有 `import_xhs_history()` 幂等同步到统一表。它的评论抽取目前没有平台原生评论 ID，因此不为接入通用服务伪造平台 ID。B 站和其他适配器走现有 `platform_service`，统一入口按平台汇总结果。

示例：

```powershell
python main.py collect-live --platform all --keyword "露营" --limit 10
python main.py collect-live --platform bilibili --content-id BVxxxxxxxxxx --limit 10
```

命令接收单个平台或 `all`，并要求提供关键词或单条内容 ID。关键词用于平台搜索；内容 ID 仅用于指定的平台，不在平台间复用，而且必须由该平台适配器支持。小红书当前实时浏览器流程使用关键词，不接收 content ID。`all` 模式逐个平台独立运行，单个平台失败不会中断其余平台。

## 登录与平台边界

- 小红书实时读取要求用户在本机可见的 Chrome 中手动登录。程序不读取或输出密码，不上传浏览器配置目录；登录后只做一次状态复核。仍处于登录墙、验证码、安全验证或限流状态时，停止该平台并说明原因，不自动解验证码、不伪造会话。
- B 站仅走现有公开 API 适配。遇到 401/403/412/429 等限制时，记录真实结果并停止该平台，不切换 IP、账号、UA 或签名。
- 其他平台沿用当前适配器的能力和授权提示。未实现或没有合法路径的平台明确跳过，不用本地旧数据冒充本次实时结果。
- 实时采集只计入本次实际取得的数据；旧的本地数据可继续用于分析，但不作为本次实时任务的成功结果。

## 数据与运行结果

每个平台的实时内容、评论继续写入统一库。访问尝试追加写入 `access_records`，至少保留平台、能力、接入模式、状态、来源、记录数、失败原因和时间。命令输出每个平台的状态、实际新增/更新条数及失败原因；部分成功不显示为全平台成功。

## 错误处理

参数错误在发起请求前返回；适配器异常按平台隔离。需要登录或授权时返回可执行指引。遇到登录验证、验证码、安全挑战、平台拒绝或限流时，停止当前平台，不重试规避。其他平台继续执行，并在最终汇总中保留失败状态。

## 验收

- `collect-live --help` 显示完整参数和“实时采集可能需要登录/授权”的提示。
- 离线测试覆盖关键词/内容 ID 参数校验、多平台逐平台隔离、登录提示、受限平台跳过、HTTP 412 不重试、访问记录和统一库写入。
- 不通过离线 mock 宣称真实平台采集成功；真实在线结果只按本次实际响应记录。
- 更新 README 与 USAGE，说明各平台的登录/授权要求和当前未支持边界。
- 不增加新的平台注册框架、数据库 schema 或运行依赖；不提交密钥、浏览器会话、数据库或采集输出。
